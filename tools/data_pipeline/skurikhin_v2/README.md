## Порядок запуска

```powershell
# Из корня репозитория
cd tools/data_pipeline/skurikhin_v2
$env:PYTHONIOENCODING='utf-8'
$env:RIVER_API_KEY='<ваш ключ api.river.ai>'
# При необходимости переопределить локальные каталоги исходников:
# $env:SKURIKHIN_INSPECT_DIR='<путь к _inspect>'
# $env:SKURIKHIN_PDF_PATH='<путь к PDF справочника Скурихина>'
# $env:SKURIKHIN_OCR_DIR='<путь к ocr_md>'
python appendix_map.py        # приложения 1–3 -> appendix_mapping.json
python assemble.py            # склейка левой и правой половин разворотов
python llm_names.py           # названия: опечатки, раскрытие по разделу, синонимы
python build_products.py      # итоговые JSON/CSV
python validate_products.py   # приёмка (должно быть 0 ошибок)
```

`llm_names.py`, `assemble.py` и `appendix_map.py` пишут кэш и промежуточные
файлы в `data/skurikhin_v2/_inspect/` (или каталог `SKURIKHIN_INSPECT_DIR`)
и при повторном запуске продолжают с места остановки.

## Модули

- `parse_ocr.py` — разбор HTML-таблиц из `ocr_md/pNNN.md`. Ключевой принцип:
  столбцы привязываются к **каноническому порядку** (`CANON_LEFT`,
  `CANON_RIGHT`, `CANON_RIGHT_ALC`), а не к индексам шапки, потому что OCR
  регулярно теряет столбцы `ОК`, `C` или `ЭЦ`. `parse_number()` отличает `0`
  от «нет данных»; `parse_alcohol()` разбирает `14,6 (18,0)**`.
- `assemble.py` — левая половина (`БЖУ`) соединяется с правой (минералы,
  витамины, `ЭЦ`) по коду; правые строки склеиваются в блоки по три
  (100 г / порция / %с.п.) и берётся **строка 100 г**, а не та, где стоит
  код; восстановленные значения `ЭЦ` подставляются из полосового
  распознавания; выполняется физическая проверка калорийности.
- `appendix_map.py` — разбор приложения 3 (масса 1 шт.) из текстового слоя
  PDF с координатами слов + нечёткое сопоставление продуктов с приложениями
  1 (несъедобная часть), 2 (меры) и 3 (`1 шт.`).
- `llm_names.py` — три прохода DeepSeek через `api.river.ai` (модель
  `deepseek-ai/DeepSeek-V4.1-Flash-1017`, пакеты по 60, 8 потоков, кэш
  JSONL): исправление опечаток OCR, раскрытие названий по разделу
  («Костромской» → «Сыр «Костромской»»), ревизия всех названий и бытовые
  синонимы.
- `manual_repairs.py` — точечные правки там, где OCR слил блоки `rowspan`'ом
  и код продукта пропал (`8.1.3.5`, `3.5.10.3`).
- `build_products.py` — итоговая схема, меры из приложения 2, несъедобная
  часть из приложения 1, масса 1 шт. из приложения 3, пересчёт бутербродов
  на 100 г (вместе с `ЭЦ`).
- `validate_products.py` — приёмка этапа 1.

## Решённые дефекты (этап 1.5)

1. **Таблица 11.2, столбец «Алк».** На `p187–p190` «Алк» помечен
   `x(y)**`, и значения уезжали в `vitamin_c` (или терялись). Теперь столбец
   определяется по позиции метки `(x,y)**`, а `energy_kcal` берётся из
   следующего числового столбца: `vitamin_c` = колонка `C`, алкоголь — только
   в `alcohol`, `energy_calc` включает `7,0 × алкоголь`.
2. **Сдвиг строки на правых страницах (22 продукта).** Код OCR ставил во
   вторую строку блока (порция 50/70/200/300 г) или в третью (`% с.п.`).
   Теперь правые строки собираются в блоки, и берётся строка 100 г —
   `3.5.2.13`, `3.5.2.14`, `3.5.2.15`, `3.5.3.3`, `3.5.10.2`, `3.6.4.2`,
   `4.1.6.5`, `4.1.6.6`, `5.4.4`, `5.4.7`, `6.1.3.5.2`, `6.1.3.5.5`,
   `6.2.1.3`, `8.1.1.8`, `8.1.4.16`, `8.1.5.15`, `8.1.5.20`, `8.1.5.21`,
   `8.1.5.23`, `10.2.3`, `10.6.4`, `11.1.1.12`, `11.1.1.13`, `12.2.11`,
   `12.2.13`.
3. **Бутерброды.** 7 продуктов, заданных на порцию, пересчитываются на 100 г
   по массе порции; `energy_calc_kcal` и `energy_book_kcal` масштабируются
   тем же коэффициентом (`3.5.2.11`: 244 → 239,6 расч.).
4. **`section_path`.** Строка «Таблица N. НАЗВАНИЕ» теперь глубина 0 и
   полностью сбрасывает путь; для таблиц 3–12, где подпись на скане не
   распознана, номер берётся из кода, а имя — из верхнего раздела. Путь
   всегда начинается с `["Таблица N. …", …]`.
5. **Опечатки и синонимы.** Исправлены `Горбушка` → `Горбуша` (`4.1.6.2`,
   `4.1.6.5`, `4.1.6.6`), `Масло какаовелла` → `Масло какао` (`5.4.4`),
   `С молочной начинкой` → `Карамель с молочной начинкой` (`10.2.3`),
   `Вина получение…` → `Вина полусухие…` (`11.2.2.2`),
   `получерствые` → `полудесертные` (`11.2.2.6`),
   `десятные` → `десертные` (`11.2.2.7`),
   `Настояк городская …` → `Настойка горькая «Русский сувенир»` (`11.2.3.1`).
   Синонимы заполнены для 1 106 из 1 108 продуктов.
6. **Приложения 1–3.** Приложение 3 разобрано из PDF (57 записей с массой
   1 шт.), нечёткое сопоставление + проверка по разделу привязало
   несъедобную часть к 126 продуктам, меры — к 136, из них `1 шт.` — к 110.

## На что обращать внимание

- `Fe` — всегда **мг на 100 г** (в книге «мг%»), без деления на 1000.
- Числа в скобках: берётся значение до скобки (`14,6 (18,0)**` → `14,6`).
- `waste_pct` — только для сырья (мясо, рыба, овощи, яйцо). У готовых блюд,
  `по 1-…`/`по 2-…`, консервов, колбас, сыров, хлеба, масла, молока, сахара —
  `null`; значения сопоставления выше 70 % отбрасываются как ошибочные.
- Меры приложения 2 присоединяются по точному или вложенному совпадению
  названия, затем — по нечёткому сопоставлению из `appendix_map.py`.
- 7 бутербродов пересчитаны с порции на 100 г, с сохранением исходной массы
  в `measures` как `порция (бутерброд)`.
- `energy_calc_kcal` считается по 4/9/3,75/3/2 ккал на грамм (алкоголь — 7);
  расхождения с книгой вынесены в `warnings` отчёта, но не считаются ошибкой,
  так как книга округляет значения. Оставшиеся 19 предупреждений —
  реальные дефекты книги/сканов (съехавшие столбцы ЭЦ, усечённые строки).
