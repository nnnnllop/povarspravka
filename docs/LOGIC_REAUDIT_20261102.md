# 2. БЛОК 0. РАССЛЕДОВАНИЕ РАСХОЖДЕНИЯ ОТЧЁТОВ (797 против 734)

## 2.1. Что происходило

Исполнитель заявил **797** тестов. Независимая проверка `flutter test --concurrency=2`
показала **734**. Обе цифры воспроизведены. **Разгадка: это одна и та же прогонка,
посчитанная двумя разными репортерами.**

```
$ flutter test --reporter json --concurrency=2      → запущено 741 настоящий тест
$ flutter test --reporter expanded --concurrency=2  → "All tests passed!" после +734
$ flutter test --reporter compact --concurrency=2   → "+734: All tests passed!"
```

## 2.2. Точная арифметика

Из JSON-репортера (`testStart`/`testDone`), 56 файлов-сьютов:

| Величина | Значение | Что это |
|---|---:|---|
| Событий `testStart` | **797** | Сюда каждый сьют добавляет **собственный скрытый тест `loading <path>`** |
| Из них `loading …` (`hidden: true`) | **56** | ровно по одному на файл; это не тесты, а маркеры загрузки модуля |
| **Настоящих тестов** | **741** | 797 − 56 |
| Расхождение plain-репортера | **−7** | 741 − 734 = 7 |

**Итог: числа «797», «734» и «741» описывают одно и то же.** 797 — артефакт подсчёта
`testStart` без фильтра `hidden`. Заявление исполнителя «797 тестов» получено
именно так: подсчётом `testStart` в JSON. Это не ошибка в коде — это ошибка в отчёте.

Подтверждение командами:

```powershell
# 1. Настоящие тесты
flutter test --reporter json --concurrency=2 > c2.jsonl
python -c "import json;n=0
for l in open('c2.jsonl',encoding='utf-8'):
    o=json.loads(l)
    if o.get('type')=='testStart' and not o['test']['name'].startswith('loading '): n+=1
print('real tests:', n)"        # → real tests: 741

# 2. Скрытые loading-маркеры
python -c "..."                 # → 56, по одному на сьют, у всех hidden:true

# 3. Plain-репортер
flutter test --concurrency=2    # → 05:57 +734: All tests passed!
```

## 2.3. Отдельная находка: **expanded/compact-репортеры переатрибутируют метки**

Это не косметика, а **дефект наблюдаемости** — он мешает независимой проверке.

При `--concurrency>1` репортеры expanded/compact печатают строку вида
`<путь файла>: <имя теста>`, но путь **не всегда соответствует файлу, к которому
относится имя**. Подсчёт по файлам из expanded-лога vs из JSON-лога:

| Файл | Тестов (JSON) | Меток в expanded | Потеряно |
|---|---:|---:|---:|
| `audit_fuzz_math_test.dart` | **105** | **2** | **103** |
| `design_audit_test.dart` | 54 | 0 | **54** |
| `audit_regression_test.dart` | 30 | 0 | **30** |
| `final360_readiness_test.dart` | 29 | 1 | **28** |
| `audit_io_unicode_test.dart` | 23 | 1 | **22** |
| `culinary_ui_test.dart` | 15 | 0 | **15** |
| `audit_fuzz_graph_memory_test.dart` | 7 | 117 | −110 (лишние) |
| `audit_math_area_b_test.dart` | 11 | 254 | −243 (лишние) |

Сумма меток 768 ≠ 741, сумма потерь 477, «лишних» 506. **Метки перемешаны между файлами.**

Причина — `flutter_tools` при параллельном прогоне печатает «текущий» файл сьюта,
к которому относится очередное *событие репортера*, а не тест, чьё имя выводится.
Дополнительно счётчик растёт на `tearDownAll` (6 событий), отсюда 741 − 734 = 7.

**Практический вывод для всех будущих проверок:** считать тесты можно **только** по
`--reporter json` с фильтром `hidden`. Проверять «сколько тестов в файле X прошло»
по plain/expanded-выводу **нельзя** — репортер соврёт.

Тест исполнителя (`audit_gost_benchmark_test.dart`) сравнивает движок **с самим собой**:

### Почему так плохо — три независимые причины

**(1) Вода участвует в теплообмене, но не во всех процессах.**
`evaporationLoss` возвращает `null` для `legacy`, `cold`, `stew`, `bake`, `grain`,
`steam` — т.е. **для 6 из 9 технологий испарение не моделируется вовсе**.
Одновременно для супов вода испаряется на 14 %, а в `stock` — на 100 %.
Итог: супы систематически занижены (−15…−56 %), а пюре и каши завышены
(+29,7 %, +31,2 %, +54,1 %), потому что их вода считается по сумме нетто.

**(2) Развариваемость задана для 3 продуктов из 12.**
`kHydrationFactors = {'гречнев': 2.1, 'рис': 2.5, 'макарон': 2.0}` — только гречка,
рис, макароны. Пшено, перловка, овсянка, манка, пшеничная крупа, кукурузная, горох,
чечевица, ячневая, пшеничные хлопья, «Геркулес», саго — **hydration = 0**.
Это дефект **RA-02**; численные следствия — в разделе 10.

**(3) Технология по умолчанию — `legacy`, т.е. «правильно = никак».**
`Dish.process` по умолчанию `HeatProcess.legacy`, а `lossProfileFor(..., legacy)`
возвращает `LossProfile.none` — **потерь нет вообще**, и `evaporationLoss(legacy)`
возвращает `null`. Пользователь, создавший новое блюдо и не выбрав технологию,
получает Б/Ж/У «как в сырье» и выход = сумма нетто. Это ровно то, что аудит-1
назвал дефектом **GOST-01** (P0).

## RA-01 (P0) — BLOCKER. Двухфайловая неатомарность: черновик и библиотека не связаны

| | |
|---|---|
| **Расположение** | [`dish_storage_repository.dart:284-330`](app/lib/data/repositories/dish_storage_repository.dart#L284-L330) (`loadAll`), `_writeAtomic` |
| **Введено** | починкой (разделение `draft.json` / `library.json` ради FUZZ-13) |
| **Статус** | ❌ ОТКРЫТ |

**Правило, которое нарушено.** «Сохранить» — это **одна** транзакция: `activeDraft`
и `savedDishes` ложатся на диск вместе или не ложатся вообще.

**Что сделано.** Очередь записи (`_tails`) защищает **каждый файл отдельно**.
Между записью `library.json` и `draft.json` нет общей точки отката. Если процесс
убит между ними (или вторая запись упала с `FileSystemException`), на диске
остаётся **новый черновик со старым списком блюд** (либо наоборот).

**Числовой пример.** Пользователь открывает блюдо, которого нет в библиотеке,
правит его и жмёт «Сохранить в библиотеку»:
1. записан `library.json` — блюда ещё нет;
2. записан `draft.json` — правки уже там;
3. процесс убит ОС (нехватка памяти / пользователь закрыл ноутбук).

Итог: при следующем старте открывается **изменённый черновик**, а в библиотеке
**старой версии блюда нет** — пользователь видит исключённое блюдо и думает,
что нажатие «сохранить» сработало.

**Гарантия, которой нет.** Нет общего `storageVersion`/поколения, по которому при
загрузке можно понять, что файлы из **разных** сохранений.

## RA-02 (P0) — BLOCKER. Развариваемость крупы задана для 3 из 12 круп → ошибка до +105 %

| | |
|---|---|
| **Расположение** | [`heat_process.dart:137-141`](app/lib/core/calculation/models/heat_process.dart#L137-L141) |
| **Введено** | починкой (новая модель выхода) |
| **Статус** | ❌ ОТКРЫТ |

```dart
static const Map<String, double> kHydrationFactors = {
  'гречнев': 2.1,
  'рис': 2.5,
  'макарон': 2.0,
};
```

**Формула.** `YieldPhysics.yieldFor` для `ProductClass.grain`:
`mass += net × k`, где `k = hydrationFactor(name) ?? null`, а при `null`
выполняется `mass += net` — **вода не добавляется вообще**.

**Числовые примеры** (выход = физика движка, `customYield = null`, `process = grain`).

| Блюдо | состав | выход приложения | масса-баланс | Δ выхода | ккал/100 г приложения | ккал/100 г при правильном выходе | **Δ** |
|---|---|---:|---:|---:|---:|---:|---:|
| Пшённая каша | 100 г пшена + 250 г воды | **350,0 г** | 500,0 г | **−150 г (−30 %)** | **87,7** | 61,4 | **+42,8 %** |
| Манная каша | 60 г манки + 300 г молока | **360,0 г** | 600,0 г | **−240 г (−40 %)** | **98,5** | 59,1 | **+66,7 %** |
| Овсяная каша | 80 г овсянки + 300 г молока + 10 г масла | **390,0 г** | 590,0 г | **−200 г (−34 %)** | **125,7** | 83,1 | **+51,3 %** |

**Почему это BLOCKER.** Каша — самый частый автоматически считаемый рецепт
на кухне. Для пшена, перловки, овсянки, манки, пшеничной, кукурузной, ячневой
крупы, гороха, чечевицы, саго, «Геркулеса», пшеничных хлопьев приложение
делит энергию **сухой** крупы на массу **без присоединённой воды**, завышая
ккал/100 г в 1,4–1,7 раза. Пользователь, который варит кашу, получит число,
которое физически невозможно: в готовой каше не может быть 98 ккал/100 г,
если в сухой крупе 199 ккал на 60 г и добавлено 300 г молока на 59 ккал.

## RA-04 (P1) — CRITICAL. `stock`: вода испаряется на 100 %

| | |

**Формула.** `yieldFor = dryMass + waterMass × (1 − loss)`, где `loss = 1.0` →

## RA-14 (P2) — MAJOR. Глобальные статические карты живут дольше документа

| | |
|---|---|
| **Расположение** | [`dish_storage_repository.dart:47-53`](app/lib/data/repositories/dish_storage_repository.dart#L47-L53) (`_libraryFingerprints`, `_draftFingerprints`, `_tails`, `_legacyByDir`, `_extraDocumentKeysByDir`, `_extraDishKeysByDir`) |
| **Статус** | ❌ ОТКРЫТ |

Шесть `static final Map<String, …>` ключом по `storageDirectory.absolute.path`:

```dart
static final Map<String, int>  _libraryFingerprints      = <String, int>{};   // :46
static final Map<String, int?> _draftFingerprints         = <String, int?>{};  // :47
static final Map<String, Future<void>> _tails             = <String, Future<void>>{}; // :67

static final Map<String, Map<String, dynamic>> _extraDocumentKeysByDir;        // :267
static final Map<String, Map<String, Map<String, dynamic>>> _extraDishKeysByDir; // :269
```

**Никогда не очищаются по жизненному циклу** (`_rememberUnknownKeys` делает
`clear()` только для **текущего** ключа при каждой загрузке — сами карты остаются).

**Дефект, доказанный чтением кода.** Быстрый путь `saveAll` пропускает запись
документа библиотеки, **не читая диск**:

```dart
if (file != null &&
    _libraryFingerprint == libraryDigest &&   // ← только память!
    !_diskLegacy &&
    await file.exists()) {
  // Библиотека на диске та же: её документ (и `.bak`) не трогаем.
```

Проверяется только `file.exists()`. Если файл **изменён извне** (второе
приложение, синхронизация облака, ручное восстановление из бэкапа), а объекты
в памяти остались **теми же** (`identical`), то:

1. `_libraryFingerprint == libraryDigest` — **истинно** (память не знает о правке);
2. `file.exists()` — **истинно**;
3. ⇒ **документ на диске НЕ перезаписывается**, хотя пользователь нажал «Сохранить».

**Числовой сценарий.** Пользователь правит блюдо в двух окнах приложения
(домашний экран + бланк — оба используют один каталог). В окне A меняет название,
в окне B жмёт «Сохранить». Окно B видит «библиотека та же» и **молча не пишет**.
Правка из A останется на диске, но `state` в B будет считать, что сохранено
**его** состояние. Это ровно тот класс дефекта, который починка объявила закрытым
(FUZZ-13/IO-05), перенесённый из области «потеря документа» в область
«тихая потеря правки».

**Прочие последствия:**
- в долгой сессии с разными каталогами — рост памяти без освобождения;
- тесты, использующие один путь (в частности `<default>`), **видят состояние
  друг друга** — изоляция тестов нарушена.

Именно поэтому идеально зелёный фаззинг **сосуществует** с провалом 36 из 37
эталонных блюд (раздел 4).

**Рекомендация для следующей итерации:** добавить свойство
`P17: per100gKcal(блюдо) ∈ [норматив × 0,9, норматив × 1,1]`, где норматив берётся
из `reference.db`. Без такого оракула фаззинг не поймает ошибку модели.

## P14 — единственное неполное свойство

Таксономия ответов на невалидный вход:

| Категория | Доля |
|---|---|
| `ArgumentError` (типизировано) | основная масса |
| `null` (движок вернул `null` вместо исключения) | **есть** |
| Тихий успех с неверным результатом | **есть** |

Это подтверждает **RA-13** (расхождение `0.1` vs `1.0`) и **RA-22**: одна и та же
невалидность даёт то исключение, то `null`, то осмысленное число — в зависимости
от того, где именно она встретилась.

## 11.4. Что означает 100 % — и что НЕ означает

**Это лучший результат, который можно получить на этом методе.** Каждое из 24
внесённых искажений — от смены коэффициента 9→8 в формуле энергии до забытого
`/100` в `fatInDish` — было обнаружено базовым набором тестов. Разброс
«пойманных тестов» показывает, насколько набор чувствителен:

| Мутант | Поймано тестов | Что это значит |
|---|---:|---|
| M03 (HALF-UP → round-down) | **109** | Округление пронизывает всё |
| M24 (`fatInDish` без `/100`) | **49** | Жир проверяется широко |
| M04 (дробные отходы) | **45** | Брутто/нетто покрыто плотно |
| M17 (per100g 3 знака) | 8 | Точечные проверки формата |
| M08, M14, M15, M16, M19, M10 | 1–2 | **Единственный тест** держит инвариант |

**Что НЕ означает:** что расчёт **верен**. Мутационное тестирование отвечает
на вопрос «заметит ли набор изменение кода», а не «правилен ли код».
Набор из 741 теста **идеально** защищает **текущую реализацию**, включая её
ошибки. Если бы `LossProfile.boilMeat` был ошибочен, все 24 мутанта всё равно
были бы пойманы, а набор остался бы зелёным.

**Синтез двух результатов — главный вывод аудита:**

| Измерение | Результат |
|---|---|
| Тесты ловят любое изменение кода | ✅ 100 % |
| Тесты обнаруживают расхождение с нормативом | ❌ 36 из 37 блюд расходятся, набор зелёный |
| Тест-эталон независим | ❌ RA-03 (сравнивает движок с собой) |

> Это и есть корневая причина провала починки: **очень качественно
> проверяется неправильная модель.** Исполнитель построил превосходную
> защиту от регресса — но не измерил, попадает ли модель в норматив.
> Поэтому «797 тестов зелёные» и «100 % мутаций поймано» **истинны**
> и **не противоречат** 36/37 провалам по нормативу.

**Что нужно добавить к набору** (одно изменение, снимающее RA-03):
оракул `per100gKcal` из `reference.db` (`is_dish = 1`) для 37 карт.
Тогда мутационный метод начнёт проверять и модель, а не только код.
